Design Philosophy

"Good AI system design is knowing when not to use AI at all."

One of the first things I think about when building an AI workflow is whether I actually need AI for the task.

Every unnecessary model call adds latency, cost, and another place for something to go wrong. If a decision can be handled with a simple rule, I usually prefer the rule.

I use AI when a task needs interpretation, context, or generation. For everything that can be clearly defined, I try to keep things deterministic.

The goal isn't to make everything "AI-powered." It's to build something that makes sense, is easier to debug, and doesn't use AI just because it's available.

01

Separate decision logic from generation

Rule-based logic handles predictable decisions. AI is reserved for tasks that require interpretation, context, or generation.

02

Use AI only where variability exists

Simple, predictable interactions use fixed responses or rules. AI is introduced when the input genuinely requires interpretation.

03

Define clear completion states

A workflow should not depend on something being "good enough." Each stage should have a clear definition of what counts as complete before the next step takes over.

04

Design for failure, not just success

Identify where failures can occur, then isolate those points so one failed component does not unnecessarily break the entire workflow.

05

Control cost through architecture

Use lightweight models or deterministic logic for simpler tasks, and reserve more capable models for tasks that actually require them.

4-Module AI Content Pipeline

A modular n8n workflow architecture that separates intake, content generation, human approval, and distribution into four independent workflows.

I originally built the content pipeline as one large n8n workflow. It worked conceptually, but the more pieces I added, the harder it became to see which part was responsible when something went wrong.

So I split it into four workflows: intake, generation, approval, and distribution. Each one has its own trigger, dependencies, and failure points.

The four modules:

  • Module 1 — Intake: Instagram webhook → intent classification → story collection → Google Sheets
  • Module 2 — Generation: Duplicate check → AI-generated content package → PostgreSQL
  • Module 3 — Approval: Telegram notification → Approve / Reject / Upload → database status update
  • Module 4 — Distribution: Approved content → Meta Graph API → Instagram / Facebook

Why split it? Each module can be worked on and debugged separately. If something breaks in one part, I can look at that part without having to untangle the entire pipeline.

Module 1 — Intake: The original design uses a lightweight local model for intent classification and a larger local model for conversational story collection.

Module 2 — Generation: The workflow checks for duplicates and then turns the collected input into a structured content package containing things like the hook, caption, and hashtags.

Module 3 — Approval: Generated content is sent to Telegram for human review. The approval decision is recorded before the content can move forward.

Module 4 — Distribution: Approved content is passed to the publishing workflow separately from the earlier stages.

Design principle: "Use AI where ambiguity actually requires it, and use rules everywhere else."

AI-Assisted Short-Form Content Workflow

A modular, five-stage prompt workflow for transforming raw Reddit stories into structured short-form content assets.

I experimented with breaking short-form content preparation into five separate prompt stages instead of asking one prompt to do everything at once.

The Problem: Turning a Reddit story into short-form content isn't just a matter of rewriting it. The story still needs to make sense, keep its emotional arc, and work within the way short-form content is actually consumed.

A single prompt can technically handle all of those tasks, but that also makes it harder to tell which part went wrong when the output isn't right.

Why Modular Instead of One Prompt? Each stage has one main job. That makes the output easier to inspect and makes individual prompts easier to change without rebuilding the whole process.

The 5-Stage Pipeline:

Stage 1: Story Extraction & Restructuring

Pulls out the important events, removes unnecessary filler, and puts the story into a clearer sequence. Output: beat-based narration structure and editor notes.

↓

Stage 2: Script Adaptation

Turns the restructured story into a short-form narration format with pacing in mind.

↓

Stage 3: Caption Generation

Generates the hook, body, and CTA while keeping the intended brand voice.

↓

Stage 4: CTA Selection

Chooses a CTA based on the kind of interaction the content is meant to encourage.

↓

Stage 5: Hashtag Classification

Groups relevant hashtags into broad, niche, and branded categories.

Honest Limitations: This is a human-in-the-loop experiment, not an autonomous content pipeline. The quality of the output still depends heavily on the quality of the source material, and fragmented stories may need manual cleanup first. There is also no feedback loop yet connecting content performance back to prompt refinement.

What I learned:

  • Breaking a large generation task into smaller stages makes the output easier to inspect.
  • It's easier to work with constraints when each stage has one main responsibility.
  • AI output still needs human review, especially when the original meaning and tone matter.
  • Modular prompts make experimentation easier because one stage can change without rewriting everything else.

Key Takeaway: The interesting part of this experiment wasn't just getting AI to generate content. It was figuring out which parts of the process should be handled by AI, which parts should stay deterministic, and where human judgment still matters.

MathDesk: AI-Assisted Math Learning Tool

A personal AI-assisted math learning tool built around a simple idea: show the reasoning behind the answer, not just the final result.

MathDesk started from something I kept noticing when using math-solving tools: getting the answer is useful, but sometimes I want to understand how the solution got there.

So I built a small math learning tool around that idea, with different AI modes for solving, learning, practicing, and navigating the app.

  • Solve: Step-by-step solutions with explanations
  • Learn: Concept-focused explanations and examples
  • Practice: Generates practice problems by difficulty
  • FAQ / Deskbot: Answers questions about using the application; it does not solve mathematics problems

Input methods: Text input with math symbols, camera/image input, handwriting canvas, upload, paste, and drag-and-drop

Model routing: Text-only requests use a text model, while image-based inputs are routed to a vision-capable model.

Tech stack: Vanilla HTML/CSS/JavaScript · n8n (self-hosted) · Groq API (Llama 3.3 70B for text · Llama 4 Scout for vision-capable inputs) · Supabase (authentication + RLS + chat history) · Docker · GitHub Pages · ngrok

My role: I designed the system architecture, built the frontend, configured the n8n workflows, integrated the Groq APIs, implemented Supabase authentication, and handled deployment, DNS configuration, debugging, and system integration. I used AI-assisted development tools during iteration, but handled the overall architecture and integration myself.

Current limitations:

  • The current deployment relies on ngrok for the n8n webhook connection.
  • Public webhook authentication still needs to be hardened.
  • Groq usage is subject to available API limits.
  • There isn't a feedback loop yet for evaluating and improving AI responses.
